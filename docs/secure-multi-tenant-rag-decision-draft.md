# Secure Multi-Tenant RAG 專案決策稿

日期：2026 年 10 月 19 日  
狀態：需求與架構決策稿，尚未開始程式實作  
定位：求職作品集與基礎教學專案  
投入：每週 6 至 8 小時，依里程碑驗收推進  
外部服務預算：每月上限 NT$300，不自動增加

本專案建立可開源的多租戶 AI 知識查詢平台，透過檢索增強生成 RAG，處理作業規定、技令手冊、料件清冊與其他指定知識資料。系統完成資料盤點、清洗、切塊、向量化與索引建置，再依使用者的公司歸屬與文件授權提供查詢、回答及來源引用。

第一版以兩家虛構公司的繁體中文文件驗證功能，先在本機執行。開源範圍是平台程式；Embedding 與回答模型沿用已選定的 OpenAI API，不宣稱模型本身開源或全部離線執行。本稿只定義需求、架構、測試與教學方式，不包含應用程式實作，也不代表已建立公開儲存庫或部署服務。

## 一 專案目的與交付邊界

專案必須同時證明兩件事：能從文件找出有依據的答案，以及能阻止未授權資料進入查詢結果與模型輸入。作品集保留真實實驗結果、失敗案例與設計理由，讓作者能解釋系統如何運作、如何驗證，以及仍有哪些限制。

| 項目 | 已確認決策 |
| --- | --- |
| 求職方向 | 先建立 AI 應用與後端的共同基礎，實作後再決定深入方向 |
| 學習方式 | 從 API、資料庫、登入開始，邊做邊教，要求能解釋、修改與驗證 |
| 第一個里程碑 | 兩家公司各自登入，文件清單只呈現自己有權閱讀的文件 |
| 執行環境 | 第一版在本機執行，之後再決定公開展示的部署方式 |
| 測試資料 | 自行編寫的虛構文件與預建帳號，不使用真實企業機密 |
| 語言 | 繁體中文文件與繁體中文提問，可包含少量英文專有名詞 |
| 版本保存 | 所有舊文件版本保留於後端，前台不提供歷史版本回查 |
| 問答方式 | 單輪問答，不帶入先前對話，不提供可重新開啟的聊天紀錄 |

## 二 新增需求與第一版的對應方式

「作業規定、技令手冊、料件清冊」是知識資料的業務分類；PDF、TXT 則是第一版接受的輸入格式。兩者分開管理，避免把支援某類文件誤寫成支援所有檔案結構。

| 需求 | 第一版落地範圍 | 後續擴充 |
| --- | --- | --- |
| 知識資料盤點 | 記錄公司、業務分類、文件名稱、擁有者、版本、來源、格式、處理狀態與授權 | 真實資料來源的自動同步 |
| 資料清洗 | 檢查格式及編碼、抽取文字、正規化可安全處理的空白與換行、記錄解析異常；保存原始內容與來源位置 | 複雜版面、OCR、進階表格整理 |
| 作業規定與技令手冊 | 使用自行編寫的文字型 PDF 或 UTF-8 TXT | 真實來源接入與更複雜的文件結構 |
| 料件清冊 | 先以明確保留料號、品名、規格與單位對應關係的文字範例驗證檢索；無法可靠解析的表格須回報失敗 | XLSX、CSV、DOCX、跨頁表格與儲存格關聯處理 |
| 資料切分 | 固定 token 長度切塊，保留來源段落、頁碼與版本 | Heading 與 Semantic Chunking |
| 向量化與索引 | OpenAI Embedding 加 PostgreSQL pgvector | 其他模型、索引與搜尋方式的比較 |
| 權限查詢 | Session 身分、tenant_id、文件授權與 RLS 共同限制存取 | 部門、群組及自訂角色 |

第一版不直接連接既有正式業務資料庫，也不自動爬取外部知識來源。「資料庫各類知識資料」先由上述文件輸入流程納入平台；新增資料庫連接器屬後續範圍。

清洗不得擅自改寫金額、日期、料號、單位、規格或規定內容。任何會影響語意的整理都需要可核對的來源；無法確認文字與欄位對應時，不得將其當作成功解析的資料。

## 三 整體技術架構

| 層次 | 選擇 | 負責內容 |
| --- | --- | --- |
| 後端語言 | Python | 業務邏輯、文件處理、檢索與評估 |
| Web 與 API | FastAPI | 身分驗證、權限檢查、操作介面與查詢服務 |
| 網頁範本 | Jinja2 | 由同一個 FastAPI 服務提供 HTML 頁面與 API |
| 登入狀態 | 後端 Session 加 Cookie | 瀏覽器攜帶隨機登入憑證，身分與權限由後端判定 |
| 資料庫 | PostgreSQL | 公司、帳號、授權、版本、背景工作與稽核紀錄 |
| 向量儲存 | pgvector | 與文件段落存於同一資料庫，提供向量相似度搜尋 |
| 資料隔離 | API 權限檢查加 PostgreSQL RLS | 同時檢查公司、帳號狀態、文件或版本權限及處理狀態 |
| 文件處理 | 背景工作 | 解析、清洗、切塊、向量化及狀態更新 |
| Embedding | text-embedding-3-small | 建立文件段落與問題向量 |
| 回答模型 | gpt-5.4-mini | 根據授權段落回答、引用與拒答 |

不同公司共用同一個資料庫與同一套資料表。受公司歸屬限制的資料，以 tenant_id 識別租戶；公司內部的文件與歷史調閱授權，再限制同公司成員的可見範圍。

原始檔、解析文字與舊版資料均由後端控管。檔案本體的儲存方式屬實作細節，但不得放在可直接公開存取的靜態檔案路徑；任何下載都必須經過身分、版本狀態與授權檢查。

## 四 公司 帳號與組織關係

第一版每個帳號只屬於一家公司，不提供跨公司切換。公司歸屬從可信的登入身分與後端資料取得，不接受使用者自行填寫的 tenant_id 作為授權依據。

帳號由測試初始化資料預先建立，不提供自行註冊、公司註冊、邀請加入或密碼復原流程。測試資料包含兩家公司，並安排管理員、主管、文件擁有者、被授權員工及未授權員工，以便驗證權限差異。

公司角色先分為「公司管理員」與「一般員工」。主管由固定的直屬主管關係判定；文件擁有者則是文件或版本上的責任關係，不是可以全公司通用的特權角色。

| 身分或關係 | 可執行操作 | 不自動取得的權限 |
| --- | --- | --- |
| 一般員工 | 上傳自己的文件、閱讀授權文件、提出自己文件的交接申請 | 其他員工的私人文件、歷史調閱與他人文件管理權 |
| 文件擁有者 | 管理自己負責的文件、設定分享、建立新版本、封存及申請交接 | 其他公司的資料與未列入交接範圍的歷史版本權限 |
| 公司管理員 | 啟用、停用本公司的預建帳號，並執行一般員工可做的操作 | 公司全部文件、修改他人文件 ACL、歷史調閱、冒用帳號或重設他人密碼 |
| 直屬主管 | 審核直屬員工提出的交接申請 | 文件內容、檔名、摘要、搜尋權、歷史調閱及自我接收權 |

第一版主管關係固定，公司管理員不能修改員工所屬公司、主管關係或任意提升角色。啟用帳號也不新增任何文件權限；帳號原有權限仍依目前文件狀態與授權判斷。

## 五 登入狀態與權限生效時間

登入成功後，後端建立 Session，瀏覽器以 Cookie 攜帶隨機憑證。Cookie 不承載可由客戶端自行決定的公司歸屬、角色或永久文件權限。Session 需要過期、登出撤銷、Cookie 安全設定與 CSRF 防護；密碼不得明文保存。

每次 API 請求都要檢查 Session、帳號是否有效及當前操作的授權。帳號被停用或文件授權被撤銷後，下一次請求即拒絕，不等 Session 過期。

問答進行期間，送入模型前及回覆使用者前再次檢查權限。第一版不串流輸出、不共用答案快取；回覆前發現權限已失效，應捨棄回答並拒絕交付。已在撤權前送給外部服務、顯示或下載的內容，無法透過後續撤權收回。

登入與授權是不同的檢查：Session 確認使用者是誰，文件授權決定這次操作能碰哪些資料。

## 六 文件閱讀與分享規則

一般員工可以上傳文件；上傳者成為擁有者，新文件預設只有擁有者可讀。擁有者可以將目前文件設定為全公司可讀，或指定同公司的有效帳號閱讀。

閱讀必須同時符合公司隔離、有效帳號、有效文件狀態及相應授權。全公司可讀只指本公司，不能對其他公司公開。指定授權不得指向另一家公司的帳號。

未授權者不能從文件清單、搜尋、摘要、回答引用、錯誤訊息或下載入口得知文件存在、檔名或內容。公司管理員及主管也受相同限制；交接審核的必要資訊例外，僅依第八節開放。

授權清單不由模型判定。檢索服務必須在取出可交付的段落時限制授權範圍；不得先將未授權段落交給模型或 Reranker，再依回答內容過濾。

## 七 文件版本 封存與後台調閱

文件更新建立新版本，保留所有舊版本與其原始內容，不覆蓋舊資料。每個版本具有穩定的識別碼、來源位置、建立時間、處理狀態及授權關係，並能關聯同一份文件。

只有目前擁有者能新增版本；新版本預設私人，不自動複製舊版本的閱讀授權。新版處理中或失敗時，原本有效的版本繼續使用；新版成功並取代舊版後，前台只使用新版。無新版權限的使用者不能自動退回查詢舊版。

原先的刪除操作改為封存。封存後，後續一般前台請求不能再搜尋、開啟或下載該文件；原始檔、段落、向量及歷史紀錄仍保留於後端。背景工作不得把已封存資料重新變成可搜尋狀態。

前台不提供版本歷史，也不允許透過舊答案引用回查已封存版本。內部紀錄仍保存回答所依據的版本，供有權限的後台人員及虛構資料評估核對；不建立對一般使用者公開的歷史答案庫。

歷史版本調閱是一項獨立權限，由該版本的擁有者授予同公司帳號。一般文件閱讀權、新版閱讀權、公司管理員身分與主管關係，都不自動附帶歷史調閱權。調閱時重新檢查帳號、公司與授權，並記錄誰、何時、調閱哪個版本。

資料模型須能分開表示目前版本的管理責任與舊版本的調閱授權。交接申請必須明列涵蓋的文件及版本範圍，不將未列入的歷史版本權限默認一併移轉。

## 八 文件交接與主管審核

交接由擁有者提出申請，包含交接範圍、建議接收人與交接原因；直屬主管核准後，系統才轉移擁有權。擁有者不能自行完成移轉。

接收人必須是同公司的有效帳號。審核主管不能批准自己接收文件；第一版不支援主管本人接手，也不加入更上一層主管的例外流程。

主管只可在自己負責的待審案件中看見申請編號、原擁有者、候選接收人與交接原因，不顯示檔名、摘要及內容。這是審核需要的有限資訊例外，不讓該文件出現在主管的搜尋或問答範圍。交接原因不得自動夾帶文件內容。

核准執行時，後端再次確認主管關係、接收人狀態、目前擁有者、文件狀態及申請是否仍有效。若資料已被其他操作更改，不能直接套用過期申請。所有必要更新須一致完成，避免同一申請重複移轉或只更新一半。

交接成功後保留原本的閱讀授權，由新擁有者接手管理並檢查。原擁有者失去交接範圍內的管理權；若仍符合全公司可讀或指定授權，且帳號有效，仍可依該授權閱讀。

員工在未提出交接申請前就被停用時，不由管理員自動接管，第一版暫不支援例外交接。既有有效閱讀授權仍依文件與版本狀態運作；停用帳號本身不能繼續操作。突然離職造成的無人管理情況，是第一版明確保留的限制。

## 九 文件處理與知識庫建置

### 支援格式與來源紀錄

第一版接受文字型 PDF 與 UTF-8 TXT。掃描 PDF、OCR、DOCX、試算表及複雜表格解析列為後續功能。能選取文字的 PDF 仍須檢查閱讀順序、段落與欄位對應，不能只以是否抽出字串判定成功。

盤點資料至少包含公司、業務分類、來源名稱、擁有者、版本、檔案格式、原始檔指紋、上傳時間、授權範圍、解析結果與處理狀態。原始來源保持可核對；解析及切塊後仍保留其來源位置。

PDF 的來源位置以實際檔案頁次為基礎，跨頁段落保留完整頁次範圍；TXT 使用解析時建立且於該版本固定的段落編號。不同版本的頁碼或段落編號不得混用。

### 背景處理流程

上傳驗證與歸屬確認 → 保存原始版本 → 解析 → 清洗與檢查 → 切塊 → Embedding → 保存段落及向量 → 確認完整性 → 標記可搜尋。

| 狀態 | 對使用者的意義 | 是否可供一般問答使用 |
| --- | --- | --- |
| 排隊中 | 已收到檔案，等待處理 | 否 |
| 處理中 | 正在解析、切塊或建立向量 | 否 |
| 可搜尋 | 必要步驟全部成功，且是目前有效版本 | 仍須符合使用者授權 |
| 失敗 | 顯示可理解的錯誤與重新嘗試入口 | 否 |
| 封存 | 資料保留供有權限者從後台調閱 | 否 |

未完成或失敗的文件不得部分進入一般索引結果。重新嘗試須避免重複建立段落與向量，記錄已完成步驟及付費呼叫；服務重啟後也須能辨識尚未完成的工作。工作執行時使用可信的公司與版本範圍，不從外部任務參數無條件接受存取身分。

### 切塊起始設定

起始值為每塊最多 600 tokens，相鄰塊重疊 60 tokens。token 不等於中文字數；以固定且有紀錄的 tokenizer 計算。切塊保留文件版本、來源頁次或段落、公司歸屬及可追溯的原文範圍。

600 與 60 是起始設定，品質由實驗判斷。後續比較 300、600、1000 tokens，明確記錄重疊規則，並保持題目、來源、授權、模型及其他條件一致。標準證據應以原文位置標記，不能只綁定某一種切塊設定才存在的 chunk ID。

## 十 檢索 回答與引用

### 檢索起始方案

使用 pgvector 精確向量搜尋，在目前有效且有權閱讀的段落中取最多前 5 段。符合條件的段落不足 5 個就回傳實際數量，不以未授權、封存或舊版段落補足。

精確搜尋是依向量距離找出真正最近的結果，不代表結果必然包含正確答案。Embedding、切塊、資料清洗與問題措辭仍會影響檢索品質。

第一個可運作基準不加入近似搜尋索引、Hybrid Search 或 Reranker。後續實驗逐項加入，避免同時更動多個因素後無法解釋差異。任何額外搜尋、排序或評分服務也只能接收已授權內容。

### 回答規則

正式問答只使用檢索到的授權內容作答，不使用模型既有知識猜測公司規定。證據不足時明確表示無法確認，例如：「目前可存取的文件中，沒有足夠資訊確認出差補助金額。」不得透露是否存在其他未授權文件。

單輪問答每次重新檢索，不帶入上一輪對話。使用者須完整表達問題；Session 維持登入，不代表保存聊天記憶。

回答模型不取得資料庫憑證，不自行授權，不直接執行任意 SQL 或依文件指令存取外部網址。文件與使用者輸入視為待處理資料，不能改變平台的存取規則。

### 引用規則

有依據的事實回答應附文件名稱與來源位置。PDF 顯示頁次，TXT 顯示段落編號；後端關聯實際使用的版本與段落，確認引用屬於該次授權檢索結果。

引用存在與引用支持答案是不同的檢查。系統與評估必須分別驗證來源是否真實、是否有權限、位置是否正確，以及內容是否支持答案。已變成舊版或封存的引用不得成為前台歷史查閱入口。

## 十一 資料庫隔離與安全設計

API 與資料庫各自落實檢查，不能把公司隔離完全交給每支 API 手動記得加入過濾條件。RLS 適用於相關文件、版本、段落、向量、授權與工作資料，並依資料用途限制可讀寫範圍。

主要邏輯資料包括公司、使用者與固定主管關係、Session、文件與版本、一般閱讀 ACL、歷史調閱授權、段落與向量、背景工作、交接申請、稽核事件與評估紀錄。實際資料表、欄位及索引在設計階段細化，本稿不先產生 SQL。

必要約束包括：授權接收人與文件屬於同公司；段落及向量指向正確版本；新版本與來源文件關聯一致；跨公司識別碼不能透過寫入或關聯造成越權。單靠 RLS 過濾讀取結果仍不足以取代資料關聯約束。

應用程式連線與背景工作不得使用能任意繞過隔離規則的資料庫超級使用者、BYPASSRLS 角色或未受約束的資料表擁有者。每次工作設定可信的租戶與使用者情境，結束後清除；測試連線重用時不會沿用上一家公司的身分。

稽核及一般日誌也須避免洩漏未授權文件資訊。公司管理員的帳號管理權，不包含瀏覽全公司文件操作明細。一般日誌不記錄密碼、Session 憑證、文件正文或完整問答；錯誤回應不得洩漏原始儲存路徑、機密檔名或其他公司的識別資料。

安全測試涵蓋應用程式中的員工、公司管理員、主管、API、背景工作與資料庫政策。具主機或資料庫最高權限的平台維運者不在租戶隔離承諾內；OpenAI API 會收到呼叫所需的虛構文件內容與問題。第一版不使用真實企業機密驗證這個架構。

## 十二 評估實驗與驗收標準

### 題庫與標準證據

先建立 30 題人工校對的核心開發題，之後擴充至至少 100 題固定的自動化驗收題。調參資料與最終驗收資料分開，保留題庫版本與建立依據；最終測試結果不能反覆拿來調參後仍宣稱是未見過的驗收結果。

每題記錄提問、測試帳號、公司、角色或關係、當時授權與版本狀態、標準答案、允許引用的原文證據，以及預期回答或拒答。涵蓋可回答、無答案、同公司未授權、跨公司相似文件、舊版與新版矛盾及 Prompt Injection。

兩家公司刻意使用語意相近而答案不同的規定，例如 A 公司出差補助為 NT$1,500、B 公司為 NT$3,000，以驗證系統有沒有因語意相似而拿錯來源。料件清冊加入相似料號、相同名稱不同規格與單位差異案例。

### 必須完成的六項實驗

| 實驗 | 比較方式 | 指標與紀錄 |
| --- | --- | --- |
| Chunk Size | 300、600、1000 tokens，記錄固定的重疊規則 | Recall@5、設定與資料版本 |
| Retrieval | Vector 與 Hybrid | Recall@5、MRR、耗時 |
| Reranker | 相同候選集合下有與無 Reranker | nDCG@5、額外延遲與成本 |
| Embedding | 起始模型與另一個 Embedding 模型 | 正確檢索率、Recall@5、費用、向量維度與模型版本 |
| RAG 回答 | 有與無檢索內容的離線對照 | Faithfulness、回答正確率、引用正確率與拒答表現 |
| 資料隔離 | 多帳號、多角色、跨公司與公司內未授權操作 | 未授權存取成功次數、洩漏位置與完整失敗案例 |

Hybrid、Reranker 與第二個 Embedding 模型的具體套件及模型，在執行該項實驗前依繁體中文需求、成本與可用環境選定並記錄。它們屬比較實驗，不改變第一個可運作基準；尚未執行時不得填寫成績。

### 指標的判讀

- Recall@5：前 5 個結果涵蓋多少預先標記的相關證據。跨切塊設定比較時，以一致的原文證據單位判定，避免重疊段落被重複計分。
- MRR：第一個相關結果排名的倒數，再對題目取平均，觀察正確證據是否出現在前面。
- nDCG@5：根據預先標記的相關程度，評估前 5 個結果的排序品質。
- Faithfulness：回答中的可驗證主張有多少受到允許使用的來源支持。
- 引用正確率：引用是否確實存在、位置正確、可授權存取，並支持對應主張。
- 拒答表現：沒有充分授權證據時是否拒答，以及有足夠證據卻錯誤拒答的比例。

無答案或沒有授權證據的題目另行評估，不套用分母為零的 Recall。無檢索模型只用於受控離線實驗，不是正式服務的猜答備援；沒有引用的對照答案，其引用指標標記為不適用，不冒充有效引用成績。

自動檢索與授權檢查優先使用可重現的判定；回答語意與來源支持度以明確評分規則及人工抽查校正。若加入模型評分，須揭露評分模型、提示與人工一致性檢查，避免把模型自評當作客觀真值。

### 安全必要驗收

在已定義的安全測試集中，未授權存取成功次數必須為 0。檢查範圍包含文件存在性與檔名、一般 API 回應、搜尋段落、送入模型或 Reranker 的內容、回答、引用、下載與背景工作。即使最後答案沒有洩漏，只要未授權內容已送入模型，也計為失敗。

測試至少涵蓋偽造 tenant_id、猜測文件或版本 ID、同公司 ACL 越權、管理員或主管繞過權限、主管自我接收、歷史調閱越權、授權撤銷、帳號停用、舊版回退、失效交接申請、連線情境殘留與惡意文件指令。

所有失敗保留測試輸入、預期、實際結果、洩漏階段、修正及重新驗證紀錄。通過測試只能表示通過已定義案例，不宣稱任何情況下都絕不洩漏。功能與安全驗收必須通過；品質與延遲則先建立基準並呈現真實比較，不預填漂亮百分比。

## 十三 預算 用量與實驗紀錄

每月外部服務預算維持 NT$300。每次付費呼叫前估算並預留最大可能用量，限制輸入、回答長度、重試次數與平行工作數；預估費用超出剩餘預算時停止付費功能，不自動換更貴模型或加預算。換算與停止點保留匯率、稅費、重試及估算誤差的空間。

同時發生的工作需要共同計算已花費與已預留用量，不能讓多個工作各自認為預算尚有餘額。API 供應商帳務與應用程式估算都要核對；平台用量控制不應宣稱能限制使用者在其他程式使用同一組金鑰產生的費用。

| 模型 | 本次決策核對的標準費率 |
| --- | --- |
| text-embedding-3-small | 每百萬輸入 tokens US$0.02 |
| gpt-5.4-mini | 每百萬輸入 tokens US$0.75，每百萬輸出 tokens US$4.50 |

上述費率僅供規劃，實際執行前再次核對。若每題 4,000 輸入及 500 計費輸出 tokens，100 次回答的費率試算為 US$0.525，約 US$0.53；不含 Embedding、重試、模型評分與其他費用，不是完整專案費用承諾。

實驗紀錄至少包含模型及版本、題庫與文件版本、chunk 設定、授權情境、檢索方法、向量維度、輸入及輸出 token 用量、失敗及重試、各階段耗時、成本估算與指標。虛構測試資料與完整評估結果獨立保存，不混入一般生產式操作日誌。

## 十四 操作介面與教學交付

同一個 FastAPI 服務提供 Jinja2 網頁及 API，介面涵蓋登入與登出、授權文件清單、上傳及處理狀態、目前版本管理、分享設定、單輪問答與引用、交接申請與主管審核、歷史版本後台調閱，以及管理員可執行的帳號啟用停用。

前台與後台是使用情境的區別，不代表後台可以略過授權。頁面按鈕只提供操作入口，每次實際請求仍由 API 與資料庫檢查。介面優先清楚呈現狀態、來源與權限差異，複雜動態互動留待後續。

| 階段 | 功能與驗收 | 作者需要能解釋的內容 |
| --- | --- | --- |
| 一 API 資料庫與登入 | 兩家公司預建帳號登入，僅看到自己可讀的文件清單；直接呼叫 API 也不能越權 | 請求與回應、資料表關聯、Session、公司歸屬與閱讀授權 |
| 二 文件權限與生命週期 | 私人與分享、版本及封存、獨立歷史調閱、主管審核交接；先完成 API 檢查，再加入 RLS | 租戶與角色差異、最小權限、版本授權、審核與一致性更新、RLS 限制 |
| 三 文件處理與 RAG | 背景解析、清洗、切塊、Embedding、精確 Top-5、回答引用及拒答 | 每個步驟輸入與輸出、檢索為何可能找錯、模型為何仍需驗證 |
| 四 評估與作品集 | 30 題基準、至少 100 題自動驗收、六項實驗、安全案例與展示報告 | 如何控制變數、判讀指標、解釋失敗與成本，以及安全承諾的界線 |

每階段包含白話說明、可觀察的實作、作者自行完成的小修改、口頭回述及驗收。能啟動服務不足以通過階段；需要能說明一次操作如何經過身分、公司、授權與資料處理流程。維持每週 6 至 8 小時，不先承諾固定完成日期。

作品集交付包含專案說明、架構與權限規則、虛構資料盤點表、可重現的測試與評估方法、真實比較報告、安全失敗與修正紀錄、展示流程及面試問答筆記。程式開源前另處理授權條款、相依套件授權及機密排除，不將 API 金鑰或真實資料納入公開內容。

## 十五 第一版限制與後續範圍

第一版不提供多公司帳號切換、公開註冊、邀請加入、密碼復原、動態主管關係、部門群組、自訂角色、主管本人接手、突然離職的例外交接、多輪聊天、前台歷史版本回查、掃描 PDF、OCR、DOCX、試算表、複雜表格、跨語言檢索、真實資料庫連接器或正式對外部署。

Heading 與 Semantic Chunking、近似向量索引，以及更完整的資料來源整合屬後續能力。Hybrid、Reranker 與第二個 Embedding 模型則仍須完成原訂比較實驗；不得以不納入起始基準為由，把這些實驗寫成已完成或直接取消。

上傳大小、頁數、問題長度、Session 時限、工作逾時與重試上限等細部值，在對應實作前依測試環境訂定並記錄，不能無限制接受輸入。這些參數不改變本稿已確認的權限與預算上限。
