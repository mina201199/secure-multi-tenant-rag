# 第二階段：文件生命週期與資料庫隔離

這是 M2 階段紀錄。最新版已加入 PDF／TXT 處理與問答，模型設定、處理上限及驗收範圍請看 [第三階段教學](milestone-3-guide.md)。

本階段加入分享、不可覆寫的版本、封存、獨立歷史授權、主管審核交接、帳號啟停與 PostgreSQL RLS。文字版本經獨立 worker 完成檢查後才切換為目前版本。PDF 上傳、解析、切塊、向量與問答仍屬第三階段。

## 啟動與升級

在專案目錄執行：

```powershell
docker compose up --build -d --wait
docker compose ps -a
```

預期 `db`、`web` 健康，`setup` 正常結束，`worker` 持續運行。入口為 http://127.0.0.1:8008/login。

既有第一階段資料會由 migration 保留為第一個版本；原始文字、密碼雜湊與閱讀名單不重設。migration 以檔名與 SHA-256 記錄已套用版本，已套用檔案不可原地修改，應新增下一支 migration。政策及受限操作函式則由 setup 在同一交易更新。

正式升級前應保存資料庫備份，並短暫停止舊 web／worker，避免舊程式存取新結構。這次本機升級的備份位置與驗證結果見 [第二階段驗收紀錄](milestone-2-verification.md)。

停止並保留資料：`docker compose --profile test down`。一般停止不要加 `-v`。

## 帳號

延用第一階段的示範密碼 `Demo-Rag-2026!`：

| 工作 | 甲公司 | 乙公司 |
| --- | --- | --- |
| 文件擁有者 | a.owner | b.owner |
| 指定閱讀員工 | a.reader | b.reader |
| 交接接收人範例 | a.outsider | b.outsider |
| 直屬主管 | a.supervisor | b.supervisor |
| 公司管理員 | a.admin | b.admin |

主管與管理員沒有額外文件閱讀權。要並排比較帳號，請使用不同瀏覽器工作階段；同一工作階段切換帳號會輪替 Session。

## 頁面操作

### 分享

登入擁有者後，前往「我管理的文件」並選擇文件。閱讀範圍可設為私人、本公司或指定同公司有效帳號。只有選擇「指定人員」時才使用勾選名單；取消勾選即撤銷該人的指定閱讀權。

每次提交綁定目前版本；若頁面開啟後版本已被替換，儲存會被拒絕，需重新載入。變更下一次請求即生效。

### 新版本與處理

在文件管理頁貼上新版完整文字。上限為 1 MiB UTF-8；本階段不接受 PDF 或實體檔案上傳。每份文件最多有一個尚未完成的版本工作。

新版本保存原文與 SHA-256，預設私人，不繼承舊閱讀名單。背景 worker 使用另一個資料庫角色處理工作。成功前仍使用舊版本；成功後原子切換，沒有新版權限的人不能回退讀取舊版。

目前文字檢查會拒絕只有空白的內容。處理失敗時舊版不受影響，可在管理頁重試，最多三次嘗試。每次租約 60 秒，worker 中斷後可重新領取到期工作；舊租約不能完成新工作。空白內容本身不會因重試而改變，應另外提交有內容的新版本。

### 封存

擁有者可封存文件。封存保留原始版本與相關紀錄，前台清單、內容與下載都不再提供該文件，未完成工作會被取消。本階段不提供解除封存或一般刪除介面。

擁有者仍可在管理頁看見封存狀態與版本資訊；這不等於取得歷史內容的閱讀權。

### 歷史調閱

「歷史調閱與授權」是獨立後台。版本擁有者可設定該版本的歷史閱讀名單，包括把自己列入。一般分享、目前版本閱讀權、主管與管理員身分，都不會自動產生歷史調閱權。

可以預先對目前版本設定歷史名單，但只有該版本成為舊版或文件封存後才適用。每次歷史內容 API 或頁面調閱都記錄操作者、時間、文件與版本。撤銷名單後，下一次請求即拒絕調閱。

歷史後台的版本管理只提供該使用者有權管理的版本識別與狀態；沒有歷史閱讀權時不會提供原文。

### 交接

文件擁有者從管理頁選定接收人、版本範圍及原因，交由固定直屬主管審核。須包含目前有效版本；歷史版本可明確勾選，未勾選者不會移轉。介面一次申請一份文件，API 支援最多 20 份文件的一致性交接。

審核人只能看到待審申請編號、申請人、接收人、原因及待審狀態，不能從審核頁取得檔名、內容或文件／版本範圍。原因由申請人自行填寫，請勿放入機密內容；系統不自動帶入文件文字。

接收人必須是同公司有效帳號，不能是申請人或審核主管。待處理版本完成前不能提出交接。核准時會重新確認所有帳號、主管關係、擁有者、文件狀態、有效版本與申請範圍；申請七天到期。分享、歷史授權或版本等變更會讓既有申請失效，需重新提出。

核准成功後保留既有一般閱讀 ACL 與歷史閱讀名單，只移轉指定的管理責任。原擁有者若仍有公開或指定閱讀權，可繼續閱讀，但不能繼續管理。多份文件在同一交易完成；同一或競爭申請不能重複移轉。

### 帳號啟停

公司管理員可在「帳號管理」啟用或停用本公司的既有帳號。停用會撤銷該帳號全部 Session；重新啟用後須重新登入，不能復用舊 Cookie。

介面不提供改角色、改主管、改公司、重設密碼或接管文件。未事先交接就停用的擁有者，其文件可能無人管理，維持決策稿的第一版限制。

## 主要 API

所有變更操作需要有效 Session、正確 Origin，以及 `X-CSRF-Token`。先用 `GET /api/csrf` 取得目前 Session 的 CSRF 值。表單則使用隱藏欄位。JSON 不接受未定義欄位，例如企圖新增 `role`、`tenant_id` 或 `owner_id`。

| API | 功能 |
| --- | --- |
| GET /api/manage/documents | 自己管理的文件，含封存狀態 |
| GET /api/documents/{id}/versions | 自己管理文件的版本資訊，不含歷史原文 |
| PUT /api/documents/{id}/sharing | `version_id`、`visibility`、`user_ids` |
| POST /api/documents/{id}/versions | 提交 `content`，回傳版本與工作 ID |
| GET /api/jobs/{id} | 管理者查詢處理狀態 |
| POST /api/jobs/{id}/retry | 重試可重試的失敗版本 |
| POST /api/documents/{id}/archive | 封存文件 |
| GET /api/documents/{id}/download | 授權下載目前版本的 UTF-8 文字 |
| PUT /api/history/versions/{id}/permissions | 取代該版本歷史閱讀名單 `user_ids` |
| GET /api/history | 自己獲准調閱的歷史版本 |
| GET /api/history/versions/{id} | 重新驗權、記錄稽核並回傳歷史內容 |
| POST /api/transfers | `recipient_id`、`reason`、`scope`（文件與明確版本陣列） |
| GET /api/transfers | 自己的申請或自己負責的待審案件 |
| POST /api/transfers/{id}/approve、reject | 主管核准／拒絕 |
| GET /api/admin/users | 管理員列出本公司帳號 |
| PUT /api/admin/users/{id}/active | 管理員設定 `is_active` |

沒有權限的資料與不存在資料使用相同 404。過期狀態或重複操作使用 409。無效接收人與不一致的版本範圍使用一般 422，不回傳資料庫原始錯誤。

## RLS 與信任邊界

- 12 張身分與業務資料表啟用並強制 RLS。一般資料讀取同時有 API 授權條件與資料庫政策。
- 每次 Session 驗證後，後端建立有 HMAC 簽章且綁定 Session 雜湊的交易區域身分。直接修改 `tenant_id`、使用者設定或簽章不能取得另一個身分；交易結束即清除情境。
- 簽章祕密存放於 web 環境及無 runtime 讀取權的 `app_private`。setup 與 web 必須使用相同 `APP_CSRF_SECRET`。worker 沒有這個祕密。
- Session 活動更新先以短交易完成，再進入單一業務交易，以免與帳號停用互相等待。業務交易在回應送出前提交或回滾。
- web 使用 `rag_app`，worker 使用 `rag_worker`；兩者都不是資料表擁有者、superuser、BYPASSRLS 或管理角色，且沒有角色成員關係。
- 一般角色不能直接改文件、擁有者或 Session。ACL 表即使具名義寫入權，也沒有允許寫入的 RLS 政策，直接 INSERT／UPDATE／DELETE 不能改資料。
- 變更經固定 `search_path` 的受限 `SECURITY DEFINER` 函式執行。這些函式由初始化管理者持有，會驗證身分、範圍、狀態及鎖定；它們是需要持續審查的受信任邊界，不是任意 SQL 入口。
- worker 從資料庫領取工作及不可猜測的短期租約，RLS 只允許讀取該工作版本；完成時再次檢查租約、帳號、擁有者、前一有效版本及封存狀態。
- 一般使用者與公司管理員沒有稽核表直接讀取權。稽核不保存正文、密碼或 Session 憑證。

主機／資料庫最高權限維運者仍屬受信任範圍。本階段未建立第三階段的段落、向量或付費用量資料表；那些表新增時也必須加入隔離與測試，不能把現有政策當作未來表格自動受到保護。

## 驗收與練習

可重現自動化測試：

```powershell
docker compose --profile test run --build --rm tests
```

測試只允許 `test-db/rag_test`，每輪會重建其中的測試 schema；不能把連線改為開發或正式資料庫。升級測試另外在同一測試主機建立一次性資料庫，驗證後刪除。

完整實際 HTTP 驗收（需要已啟動的 web／worker）：

```powershell
docker compose run --rm -T --no-deps setup python -m tests.smoke_milestone2
```

該命令只借用 setup 的初始化憑證建立一份虛構驗收文件，所有後續業務操作走真實 HTTP。成功後留下已封存的範例與稽核紀錄，終端顯示文件／版本／申請 ID。不要在真實企業資料環境執行示範帳號驗收。

自行練習：

1. 用擁有者將私人文件指定分享給 reader，驗證 outsider 仍不能讀取，再撤銷 reader。
2. 建立新版後解釋為何舊版可繼續使用、為何新版成功後 reader 可能失去權限。
3. 解釋一般閱讀、版本擁有者及歷史調閱三者的差異。
4. 提出交接後再修改分享，確認主管不能核准原申請。
5. 說明 RLS 為何不能只信任使用者送來的公司 ID，以及 worker 為何需要獨立的工作情境。

作者的自行練習與口頭回述尚未由自動化測試代替完成。實測範圍與結果見 [第二階段驗收紀錄](milestone-2-verification.md)。
